# 第一部分 · 知识讲解

## 1. 什么是自动化测试

前六天验证代码的方式是：运行程序、手动输入、看输出对不对。这叫**手动测试**，它有三个无法克服的问题：

- **改了 A 功能，只会去试 A**，不会把 B、C、D 再试一遍
- **边界情况靠记忆**（空列表、0、超范围），总会漏
- **人越累越容易漏**，而改代码往往发生在赶进度的时候

自动化测试就是**用代码验证代码**：把「什么输入应该得到什么输出」写成代码，一条命令跑完全部。

核心价值是**一次写、无限次跑**。写测试的成本是一次性的，收益随着代码修改次数累积。

## 2. `assert` 语法

```python
assert 表达式
assert 表达式, "失败时的提示信息"
```

语义是「**我断定这个表达式为真**」：

- 为真 → 什么都不发生，程序继续
- 为假 → 抛出 `AssertionError`，程序停在这一行

```python
assert check_num(30, 50) == "小了"      # 通过，无输出
assert check_num(30, 50) == "大了"      # AssertionError
```

**一串 `assert` 全部通过时没有任何输出**——这是正常的，不是「没跑」。初学时容易因为看不到输出而怀疑测试没执行。

带提示信息的版本在失败时更有用：

```python
assert result == expected, f"预期 {expected}，实际得到 {result}"
```

## 3. 容易写错的断言：条件恒为真

```python
assert check_num(30, 50)                  # 永远通过
assert check_num(30, 50) == "小了"        # 真正的断言
```

第一个**永远不会失败**，因为 `check_num` 返回的任何非空字符串都是真值（Day01 讲的真值测试）。这种测试写了等于没写。

同类的坑：

```python
assert items                   # 只验证了「非空」，没验证内容
assert len(items) == 3         # 只验证了长度，没验证元素对不对
```

**写完断言问一句：有没有可能让它失败？** 想不出能让它失败的输入，这个断言就是无效的。

## 4. 重要：`assert` 在 `-O` 模式下会被完全移除

```bash
python -O script.py
```

`-O`（optimize）模式下，**Python 会把所有 `assert` 语句直接删掉**，就像它们不存在一样。

这带来一条硬性规则：

> **`assert` 只能用于测试和内部不变量检查，绝不能用于生产代码的输入校验。**

```python
# 错误：用 assert 校验用户输入
def parse_age(s):
    age = int(s)
    assert 0 <= age <= 150, "年龄不合法"      # -O 模式下这行消失，校验失效
    return age

# 正确：用 raise
def parse_age(s):
    age = int(s)
    if not 0 <= age <= 150:
        raise ValueError("年龄不合法")
    return age
```

区分标准：

| 用途 | 该用什么 |
|---|---|
| 测试代码里验证预期 | `assert` |
| 检查「这里绝不可能发生」的内部不变量 | `assert` |
| 校验外部输入（用户、文件、API） | `raise` |

Day09 会正式学 `raise`。

## 5. 测试函数的组织与命名

```python
def test_check_num() -> None:
    assert check_num(30, 50) == "小了"
    assert check_num(50, 50) == "正确"
    assert check_num(70, 50) == "大了"
```

三条惯例：

**一、函数名以 `test_` 开头。** 这不是语法要求，而是**测试框架的发现约定**——pytest 会自动找出所有 `test_` 开头的函数来执行（Day21 会用上）。现在遵守，以后换框架不用改名。

**二、测试函数里不要有 `input()` 和 `print()`。** `input()` 会让测试卡住等人输入（自动化就谈不上了）；`print()` 会干扰测试输出，而且报告结果应该靠断言失败时的异常，不是靠打印。

**三、定义了测试函数必须调用它。**

```python
def test_check_num():
    assert ...

test_check_num()          # ← 没有这一行，上面的断言一次都不会执行
print("所有测试通过！")      # 这个 print 放在测试函数外面
```

`def` 只是定义（Day04 讲过），不调用就不执行。交给 pytest 时会自动调用，但在只用 `assert` 的阶段必须手动调。

## 6. 该测什么：三类输入

写测试时容易只测「正常情况」，但 bug 大多藏在另外两类：

| 类型 | 例子（针对 `check_num(input, target)`） |
|---|---|
| **正常值** | `(30, 50)`、`(70, 50)` ——典型的大于、小于 |
| **边界值** | `(50, 50)` 相等、`(1, 100)` 最小、`(100, 1)` 最大 |
| **异常值** | 非整数、`None`、超范围 |

**边界值最容易出错**，因为它们正好落在 `<` 和 `<=` 的分界上。Day06 那个「`0` 被放过」的 bug 就是边界问题。

一个实用的检查清单：

- 相等的情况测了吗？
- 最小值、最大值测了吗？
- 空集合测了吗？
- 刚好超出范围一点（如 `101`）测了吗？

## 7. 验证测试本身有效：故意改错代码

**一个永远不会失败的测试，和没有测试是一样的。**

写完测试后应该做一次反向验证：

```python
def check_num(input_num, target_num):
    if input_num != target_num:        # 故意把 == 改成 !=
        return "正确"
```

再跑测试，应该看到 `AssertionError`。看到报错，才证明这套测试真的在起作用。然后把代码改回来。

这一步能发现三类问题：断言写错了对象、测试函数没被调用、断言条件恒为真（见第 3 节）。

## 8. 回归测试

上面那个「改错代码 → 测试报警」的过程，正是**回归测试**的原理：

> 以后修改代码时，已有的测试会告诉你有没有破坏旧功能。

「回归」指的是「功能退回到了错误状态」。这是测试最大的长期价值——它让你**敢改代码**。没有测试时，改一处要担心影响到哪里；有测试时，跑一遍就知道。

## 9. 可测试性来自设计

`check_num()` 之所以能三行测完，是因为它**只做一件事**：接收两个数字，返回一个字符串。

```python
assert check_num(30, 50) == "小了"       # 直接传参、直接断言返回值
```

它没有 `input()`、没有 `print()`、不碰随机数、不读文件。这种函数叫**纯函数**：

- 相同输入永远得到相同输出
- 不产生副作用（不修改外部状态、不做 IO）

**纯函数是最容易测试的代码。** 反过来，如果判断逻辑写在主循环里、结果直接 `print` 出去，想测就得模拟键盘输入、捕获标准输出。

> 这正是 Day04 那个 A/B 设计题的实际回报：当时选择「返回结果而不是打印」，今天才能这么轻松地写测试。
>
> **设计决定可测试性。** 测试写不出来，往往不是测试技术的问题，而是被测代码的结构有问题。

## 10. 测试代码也要能被读懂

测试是一种文档——它说明了「这个函数应该怎么表现」。所以测试代码本身也该清楚：

```python
# 不好：看不出在测什么
assert f(1, 2) == 3

# 好：意图明确
def test_猜小了时返回提示():
    assert check_num(30, 50) == "小了"
```

实践中常见的结构是「一个测试函数只测一个场景」，函数名直接说明场景。这样测试失败时，光看名字就知道哪个行为坏了，不用去读断言。

本节还是把三个场景写在一个函数里，Day22 会学 pytest 之后再拆开。

# 第二部分 · 当天的练习

## 一、题目

不重写游戏，只给已有的 `check_num()` 写测试。

```python
def check_num(input_num: int, target_num: int) -> str:
    if input_num == target_num:
        return "正确"
    elif input_num < target_num:
        return "小了"
    else:
        return "大了"
```

要覆盖的情况：

| 输入 | 目标 | 预期 |
|---:|---:|---|
| 30 | 50 | `"小了"` |
| 50 | 50 | `"正确"` |
| 70 | 50 | `"大了"` |
| 1 | 100 | `"小了"` |
| 100 | 1 | `"大了"` |

要求测试函数里不出现 `input()` 或 `print()`。

## 二、代码

```python
def check_num(input_num: int, target_num: int) -> str:
    if input_num == target_num:
        return "正确"
    elif input_num < target_num:
        return "小了"
    else:
        return "大了"


def test_check_num() -> None:
    assert check_num(30, 50) == "小了"
    assert check_num(50, 50) == "正确"
    assert check_num(70, 50) == "大了"
    assert check_num(1, 100) == "小了"
    assert check_num(100, 1) == "大了"
```

一次写对，三件事都做到了：三个分支全覆盖、带了边界值 1 和 100、测试里没有任何交互代码。

### `assert` 是什么

```python
assert check_num(30, 50) == "小了"
```

意思是「我断定这个表达式为真」。为真则什么都不发生，程序继续；为假则抛出 `AssertionError`，程序停在这一行。

所以一串 `assert` 全部通过时**没有任何输出**——这是正常的，不是没跑。

## 三、坑：定义了测试函数，但没有调用

`def test_check_num()` 只是**定义**，不是**执行**。文件跑完，这个函数一次都没被调用，所有断言都没生效。

要在文件末尾加上调用：

```python
test_check_num()
print("所有测试通过！")
```

这个 `print` 放在测试函数**外面**——函数内部要保持纯粹，不掺输出。

**注意：`Day7.py` 的最终代码里没有加这行调用**，所以直接运行那个文件实际上什么都没测。复习时要留意。

> 后面 Day 21 用 `pytest` 之后就不需要手动调用了：pytest 会自动发现所有 `test_` 开头的函数并执行。这也解释了为什么函数名要以 `test_` 开头——不是规矩，是给测试框架认的。

## 四、精华：验证测试本身是否有效

写完测试别急着庆祝。**一个永远不会失败的测试，和没有测试是一样的。**

验证方法是故意把被测代码改错：

```python
def check_num(input_num: int, target_num: int) -> str:
    if input_num != target_num:        # 把 == 改成 !=
        return "正确"
    ...
```

再跑测试，应该看到：

```text
AssertionError
```

看到报错，才证明这套测试真的在起作用。然后把代码改回来。

这一步容易被跳过，但它能发现一类很尴尬的问题：断言写错了对象、测试函数没被调用、断言条件恒为真（比如写成 `assert check_num(30, 50)` 漏掉了 `== "小了"`——非空字符串永远为真，这个测试永远通过）。

> `assert check_num(30, 50)` 和 `assert check_num(30, 50) == "小了"` 看起来差不多，前者**永远通过**，因为任何非空字符串都是真值。这类「假测试」只能靠故意改错来暴露。

## 五、回归测试

上面这个「改错代码 → 测试报警」的过程，就是回归测试的原理：

**以后修改代码时，已有的测试会告诉你有没有破坏旧功能。**

手动测试做不到这一点。手动测的问题是：

- 改了 A 功能，只会去试 A，不会把 B、C、D 再试一遍
- 边界情况（空列表、0、超范围）靠记忆，总会漏
- 人越累越容易漏，而改代码往往发生在赶进度的时候

自动化测试是**一次写、无限次跑**。

## 六、为什么 `check_num()` 能被测试

关键在它只做一件事：接收两个数字，返回一个字符串。没有 `input()`，没有 `print()`，不碰随机数。

所以：

- 测试时直接传参、直接断言返回值，三行搞定
- 以后把游戏改成网页服务，这个函数**原样就能用**——因为它不依赖终端

反过来，如果判断逻辑写在主循环里、结果直接 `print` 出去，想测就得模拟键盘输入、捕获标准输出。这就是 Day 04 那个 A/B 设计题的实际回报：**当时选择「返回结果而不是打印」，今天才能这么轻松地写测试。**

## 整理时发现的实际问题

课件里的「现在回头看」多数是风格建议，但下面五处是**实测确认的真问题**。
共同点：**都不报错、不警告**，所以一直没被发现。

**1. `Day7.py` 没有调用 `test_check_num()`** —— 直接运行那个文件什么都不会测。

**2. `Day10/test_game.py` 的测试一次都没跑过** —— 断言包在 `if __name__ == "__main__"` 里，
而 pytest 是导入而非直接运行测试文件，实测 `collected 0 items`。见 [Day10](Day10.md) 第六节。

**3. `Day12/history.py` 的 `open()` 丢了 `encoding="utf-8"`** —— 遇到非 ASCII 内容会崩。
实测在 locale 编码为 `cp936` 的环境下抛 `UnicodeDecodeError`，而该函数只捕获
`FileNotFoundError` 和 `JSONDecodeError`，这个异常会一路上抛。见 [Day12](Day12.md) 第四节。
**注意设了 `PYTHONUTF8=1` 会掩盖它。**

**4. `Day15/day_15.py` 的 `except ValueError` 是死代码** ——
`requests.exceptions.JSONDecodeError` 同时继承 `RequestException` 和 `ValueError`，
而 `except RequestException` 写在前面先匹配上了。后果是 JSON 解析失败时提示「请求失败」，
把排查方向带向网络问题。见 [Day15](Day15.md) 第四节。
**这个问题当时没被发现，代码评审也判了「基本通过」。**

**5. `Day16/day_16.py` 的两处 `except ValueError` 同样是死代码** —— 原因与第 4 条相同，
但后果更严重：**日志会把「响应格式不对」记成「HTTP 请求失败」**，而日志是排查生产问题的唯一依据。
见 [Day16](Day16.md) 第四节。注意这一版是「优化后的参考代码」，问题出在参考答案里。

### 关于第 4、5 条的通则

**凡是用到异常继承，就必须确认 `except` 的书写顺序**——具体的异常要在宽泛的异常前面，
顺序错了后面的分支就是死代码，而 Python 不报错也不警告。

这个坑在 Day14 → Day15 → Day16 连踩三次，到 [Day17](Day17.md) 被正面指出并改对
（把 `ValueError` 提到了 `RequestException` 前面）。**复习时建议按 Day14 → 17 连起来看。**

可操作的检查方法：每写完一组 `except`，问一句「后面的分支会不会被前面抢先捕获」，
涉及继承关系就查一下 `__mro__`。

**遗留**：Day16 和 Day17 的 `main()` 里顺序仍然是错的（`RequestException` 在 `ValueError` 前），
只修了函数内部那一处。同一个问题在同一个文件的两个位置，很容易只改一半。

### 对根目录 README 待办的一条修正

根目录 `README.md` 写着「Day12、Day14 用 `type(x) != list` 的地方该换成 `isinstance`」。
对 `list` 的检查这么改没问题，但**对 `int` 的检查不能改**——`bool` 是 `int` 的子类，
`isinstance(True, int)` 为真，JSON 里的 `true` 会被当成合法数字通过校验。
详见 [Day11](Day11.md) 知识讲解第 6 节。

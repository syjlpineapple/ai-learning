# 一、概念与原理

## 1. 异常是什么

程序运行中遇到无法继续的情况时，Python 会**抛出异常**：

```text
ValueError: invalid literal for int() with base 10: 'abc'
```

它不只是「程序崩了」，而是一套**信息传递机制**，带着四样东西：

| 信息 | 例子 | 作用 |
|---|---|---|
| **类型** | `ValueError` | 哪一类问题 |
| **消息** | `invalid literal for int() with base 10: 'abc'` | 具体细节 |
| **Traceback** | 从哪一行、经过哪些函数调用过来的 | 定位 |
| **传播** | 沿调用链向上，直到有人处理 | 让合适的地方来处理 |

### 为什么不用返回值表示失败

另一种做法是让函数失败时返回一个特殊值，比如 `-1` 或 `None`：

```python
n = parse(raw)       # 失败时返回 -1
total += n           # 忘了检查 —— -1 被当成正常值加进去了
```

**调用方很容易忘记检查**，错误就被静默吞掉，带着错误的数据继续往下跑。

异常的好处是**不处理就会炸**。你忘了处理，程序会停下来告诉你，而不是悄悄算出一个错误的结果。

> 这两种做法各有适用场景，第 4.5 章「错误语义设计」专门讨论什么时候该返回 None、什么时候该抛异常。
> 这一章的 `parse_int` 返回 None，到那一章会看到这个选择的代价。

## 2. 常见的内置异常

```text
1. 常见内置异常的原文
   int("abc")           → ValueError: invalid literal for int() with base 10: 'abc'
   "a" + 1              → TypeError: can only concatenate str (not "int") to str
   [1, 2][5]            → IndexError: list index out of range
   {}["k"]              → KeyError: 'k'
   1 / 0                → ZeroDivisionError: division by zero
   None.upper()         → AttributeError: 'NoneType' object has no attribute 'upper'
   int(None)            → TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'
   undefined_name       → NameError: name 'undefined_name' is not defined
```

| 异常 | 什么时候抛 |
|---|---|
| `ValueError` | **类型对，但值不合法** |
| `TypeError` | **类型本身就不对** |
| `IndexError` | 下标越界 |
| `KeyError` | 字典里没有这个键 |
| `AttributeError` | 对象没有这个属性或方法 |
| `ZeroDivisionError` | 除以零 |
| `NameError` | 用了没定义的名字 |

### `ValueError` 和 `TypeError`：看第一行和第七行

```text
int("abc")    → ValueError    ← 字符串可以转整数，只是这个字符串的内容不行
int(None)     → TypeError     ← None 根本不是 int() 能接受的类型
```

**一句话：类型对但值不行是 `ValueError`，类型本身就不对是 `TypeError`。**

这个区分有实际意义，练习 2 会用到：用户输入的内容不对是 `ValueError`（用户的问题），给函数传了 `None` 是 `TypeError`（**写代码的人的问题**）。两者不该用同一种方式处理。

## 3. `try / except`

```python
try:
    num = int(raw)           # 可能抛异常的代码
except ValueError:
    print("输入无效")         # 抛出 ValueError 时执行
```

执行逻辑：

1. 执行 `try` 块
2. **没有异常** → 跳过所有 `except`，继续往下
3. **抛出了异常** → **立刻中断 `try` 块的剩余部分**，去找匹配的 `except`
4. 找到就执行它，然后继续往下；找不到就继续向上抛

**第 3 点的「立刻中断」很重要**，配套示例专门演示了它：

```python
def trace(raw):
    steps = []
    try:
        steps.append("try")
        int(raw)
        steps.append("try 的后半段")
    except ValueError:
        steps.append("except")
    ...
```

```text
2. 四个块的执行顺序
   trace('42')  = ['try', 'try 的后半段', 'else', 'finally']
   trace('abc') = ['try', 'except', 'finally']
```

**`int("abc")` 抛异常的那一刻，「try 的后半段」就再也不会执行了。**

## 4. 捕获的几种写法

```python
except ValueError:                   # 捕获一种
except (ValueError, TypeError):      # 捕获多种，写成元组
except ValueError as e:              # 拿到异常对象
except Exception:                    # 捕获几乎所有异常（慎用）
```

### `as e`：拿到异常对象

```text
5. except ... as e 结束后，e 会被删除
   块内：type=ValueError  str="invalid literal for int() with base 10: 'x'"
         args=("invalid literal for int() with base 10: 'x'",)
   块外：NameError: cannot access local variable 'e' where it is not associated with a value
```

| 写法 | 得到什么 |
|---|---|
| `type(e).__name__` | 异常类型名 `'ValueError'` |
| `str(e)` | 消息 |
| `e.args` | 构造异常时传入的参数元组 |

**注意最后一行：`except` 块结束后，`e` 这个变量会被 Python 自动删除。** 想在块外用它，得在块内先赋给另一个变量。

这个行为的报错措辞取决于位置：

| 在哪里访问 | 报错 |
|---|---|
| 函数里 | `cannot access local variable 'e' where it is not associated with a value` |
| 模块顶层 | `name 'e' is not defined` |

`mypy` 能在运行之前发现这个问题，它会报 `Trying to read deleted variable "e"`。

> **如果后面不用 `e`，就不要写 `as e`**——`ruff` 会提示变量未使用。

## 5. ⚠️ 不要写裸 `except:`

```python
try:
    ...
except:          # 什么都不写 —— 不要这样
    ...
```

裸 `except` 会接住**所有**异常，包括 `BaseException` 下面那些不该被接住的：

```text
4. 裸 except 会接住 SystemExit 和 KeyboardInterrupt
   裸 except 接住了 sys.exit(3) —— 程序没有退出
   裸 except 接住了 KeyboardInterrupt —— Ctrl+C 失效
   except Exception 放过了 KeyboardInterrupt —— 这才是想要的
```

第 1.3 章讲过 `sys.exit()` 的本质是 `raise SystemExit`。现在看完整的继承关系：

```text
BaseException
 ├── SystemExit           ← sys.exit()
 ├── KeyboardInterrupt    ← 按 Ctrl+C
 └── Exception            ← 「正常的」错误都在这下面
      ├── ValueError
      ├── TypeError
      └── ...
```

| 写法 | 接住 `ValueError` | 接住 `SystemExit` | 接住 `KeyboardInterrupt` |
|---|---|---|---|
| `except ValueError:` | ✓ | ✗ | ✗ |
| `except Exception:` | ✓ | ✗ | ✗ |
| **`except:`** | ✓ | **✓** | **✓** |

**裸 `except` 会让程序没法用 Ctrl+C 中断，也没法用 `sys.exit()` 退出。** 一个写在循环里的裸 `except`，可能让你只能去任务管理器里杀进程。

`except Exception` 不会接住这两个，但它也有问题：它会把**你自己代码里的 bug** 一起吞掉（第 4.3 章细讲）。**能写具体的异常类型，就写具体的。**

## 6. 完整结构：`try / except / else / finally`

```python
try:
    num = int(raw)
except ValueError:
    print("格式错误")
else:
    print(f"转换成功：{num}")
finally:
    print("无论如何都会执行")
```

| 块 | 什么时候执行 |
|---|---|
| `try` | 总是执行（但抛异常后剩余部分跳过） |
| `except` | 抛出了**匹配**的异常 |
| `else` | `try` **没有**抛出任何异常 |
| `finally` | **无论如何**都执行 |

### `else` 的用途：让 `try` 尽量小

`else` 很容易被忽略。它的用途是**把「成功后才该做的事」从 `try` 里拿出来**：

```python
# 不好：print 也在 try 里
try:
    num = int(raw)
    print(f"转换成功：{num}")      # 如果这一行出错，也会被当成「格式错误」
except ValueError:
    print("格式错误")

# 好：try 里只有可能出错的那一行
try:
    num = int(raw)
except ValueError:
    print("格式错误")
else:
    print(f"转换成功：{num}")
```

**`try` 越小，越不容易误捕获。** 第 9 节会看到误捕获的具体后果。

### `finally` 的用途：清理

```text
3. finally 一定执行，包括 return 的时候
   finally 执行了（在 return 真正返回之前）
   返回值：try 里的 return
```

`try` 里已经 `return` 了，`finally` 依然会在函数真正返回之前执行。它的典型用途是**释放资源**：关闭文件、断开网络连接。第 7.2 章写 `APIClient` 时会用到。

### ⚠️ 不要在 `finally` 里写 `return`

```text
   ⚠ finally 里写 return 的后果：
   finally_overrides() = 2      ← try 里明明 return 1
   finally_swallows()  = 'finally 的 return'  ← ValueError 消失了
```

```python
def finally_overrides():
    try:
        return 1
    finally:
        return 2          # 覆盖了 try 的返回值

def finally_swallows():
    try:
        raise ValueError("这个异常会消失")
    finally:
        return "finally 的 return"     # 异常被吞掉了
```

**第二个更危险**：一个本该向上抛出的异常，**静默消失了**，没有任何痕迹。

`ruff` 的 `SIM107` 规则会拦住第一种写法（配套代码里加了 `noqa` 才能通过检查）。Python 3.14 起解释器本身也会对这类写法给出 `SyntaxWarning`（[PEP 765](https://peps.python.org/pep-0765/)），理由正是它会吞掉异常，未来版本可能直接改成语法错误。3.13 及更早的版本不会警告，所以要靠 `ruff` 拦。

> **规则：`finally` 里只做清理，不写 `return`、`break`、`continue`。**

## 7. 两种风格：LBYL 与 EAFP

处理「可能失败的操作」有两种思路：

**LBYL**（Look Before You Leap，先看再跳）——第 1.2 章的做法：

```python
if looks_like_int(raw):
    num = int(raw)
else:
    print("不是整数")
```

**EAFP**（Easier to Ask Forgiveness than Permission，先做再道歉）：

```python
try:
    num = int(raw)
except ValueError:
    print("不是整数")
```

### 实测对比

```text
6. LBYL 和 EAFP 在哪里分歧
   '42'       LBYL=True   EAFP=42
   '-5'       LBYL=True   EAFP=-5
   ' 7 '      LBYL=True   EAFP=7
   '²'        LBYL=False  EAFP=None
   'abc'      LBYL=False  EAFP=None
   '1_000'    LBYL=False  EAFP=1000     ← 不一致
   '1__000'   LBYL=False  EAFP=None
   '_1'       LBYL=False  EAFP=None
```

`'1_000'` 是第 1.2 章留下的那处差异。EAFP 版本自然地处理对了——**而且后面两行说明它还知道下划线的规则**：`1__000`（连续两个）和 `_1`（开头）都不合法。这些规则 LBYL 版本要一条条手写，EAFP 一条都不用写。

| | LBYL | EAFP |
|---|---|---|
| 判断标准 | 你自己写的检查逻辑 | **操作本身** |
| 会和真实规则不一致吗 | **会**，每条规则都可能漏 | **不会**，判断标准就是 `int()` |
| 需要知道什么 | 所有合法格式的规则 | 只需要知道会抛什么异常 |

**Python 社区更偏向 EAFP。** 理由很朴素：「什么样的输入能成功」这件事，交给那个操作自己判断最准确。

### LBYL 根本做不对的场景

```python
if os.path.exists(path):      # 检查时文件还在
    open(path)                # 打开时文件可能已经被别的程序删了
```

检查和使用之间有时间差，这段时间里状态可能变化。这类问题叫 **TOCTOU**（Time Of Check to Time Of Use）。**只有 EAFP 能避免**——直接 `open`，失败了处理 `FileNotFoundError`。第 4.1 章会用到。

> LBYL 也有适用的地方：检查成本很低、失败代价很高、而且检查条件和真实规则确定一致的时候。
> 比如第 1.2 章的范围检查 `1 <= guess <= 100`——那是**你自己定义的业务规则**，不存在「和谁不一致」的问题。

## 8. EAFP 版的 `parse_int`

```python
def parse_int(raw: str) -> int | None:
    try:
        return int(raw)
    except ValueError:
        return None
```

两个细节：

**一、只捕获 `ValueError`，不捕获 `TypeError`。** `raw` 声明的类型是 `str`。如果有人传了 `None` 进来，`int(None)` 抛的是 `TypeError`——**那是调用方写错了**，应该让它暴露，而不是悄悄返回 `None`。

捕获 `TypeError` 会把「用户输错了」和「程序写错了」混成一回事。

**二、`return` 直接写在 `try` 里。** 这里 `try` 块只有一行，它就是唯一可能出错的操作，所以不需要 `else`。如果成功后还有别的事要做，那些事放进 `else`。

## 9. ⚠️ `try` 包得太大，会把 bug 伪装成用户的错

```python
def bonus_wide(raw_guess: str, bonus_text: str) -> str:
    try:
        guess = int(raw_guess)      # 用户输入，可能输错
        bonus = int(bonus_text)     # 程序配置，不该出错
        return f"得分 {guess + bonus}"
    except ValueError:
        return "输入无效"
```

```text
7. try 包得太大，会把程序自己的 bug 伪装成用户的错
   bonus_wide('5', '10')    = '得分 15'
   bonus_wide('abc', '10')  = '输入无效'   ← 正确：用户输错了
   bonus_wide('5', '10分')  = '输入无效'   ← 错误：是配置写错了
```

第三行：配置里把 `10` 写成了 `10分`。这是**程序的 bug**，本该是一个响亮的报错，traceback 直接指到那一行，开发者一眼就知道该去改配置。

现在它被伪装成了「输入无效」。**用户怎么改输入都没用**，而开发者看到的只是一堆「用户输错了」的反馈，根本不会想到去查配置。

### 修法：`try` 只包住「这个 `except` 准备处理的那种失败」

```python
def bonus_narrow(raw_guess: str, bonus_text: str) -> str:
    try:
        guess = int(raw_guess)
    except ValueError:
        return "输入无效"

    bonus = int(bonus_text)          # 在 try 外面，出错就让它报错
    return f"得分 {guess + bonus}"
```

**判断标准**：这个 `except` 是为了处理哪一种失败？只把会产生这种失败的代码放进 `try`。其他代码的失败是另一回事，要么有它自己的 `except`，要么就让它报错。

> 这条原则贯穿整门课。附录 A 里有一个真实案例：`except` 写得太宽，
> 日志把「响应格式不对」记成了「HTTP 请求失败」，排查方向被带偏了三章。

# 三、常见错误

| # | 错误 | 表现 | 怎么避免 |
|---|---|---|---|
| **1** | **裸 `except:`** | Ctrl+C 失效，`sys.exit()` 不退出 | 写具体的异常类型 |
| **2** | **`try` 包得太大** | 程序的 bug 被伪装成用户的错 | 只包住这个 `except` 要处理的那一行 |
| **3** | **`finally` 里写 `return`** | 覆盖返回值；**异常静默消失** | `finally` 只做清理 |
| **4** | **捕获了不该捕获的 `TypeError`** | 调用方传错类型被悄悄当成「输入无效」 | 只捕获你预期会发生的异常 |
| **5** | **在 `except` 块外用 `e`** | `NameError` / `UnboundLocalError` | 块内先赋给别的变量 |
| **6** | **LBYL 检查条件和真实规则不一致** | 合法输入被拒绝、非法输入被放行 | 能用 EAFP 就用 EAFP |
| **7** | **`except` 里什么都不做（`pass`）** | 错误被吞掉，没有任何痕迹 | 至少记一条日志（第 4.4 章） |

**第 2、3、7 条的共同点是「错误消失了」。** 异常机制的价值就在于「不处理就会炸」，这三种写法都把这个价值抵消掉了。

---

# 四、本章小结

```text
异常 = 类型 + 消息 + traceback + 向上传播
   └─ 比「返回 -1」好：不处理就会炸，不会静默算错
        ↓
ValueError（值不对）vs TypeError（类型不对）
        ↓
try / except / else / finally
   ├─ 抛异常后 try 剩余部分跳过
   ├─ else：成功后才做的事，让 try 尽量小
   ├─ finally：一定执行，用于清理
   └─ ⚠️ finally 里 return 会吞掉异常
        ↓
⚠️ 裸 except 接住 SystemExit / KeyboardInterrupt
        ↓
LBYL vs EAFP：EAFP 的判断标准就是操作本身，不会不一致
   └─ 1.2 留下的 1_000 问题在这里解决
        ↓
⚠️ try 包大了 → 程序的 bug 被伪装成用户的错
```

一句话总结：**异常处理的目的不是「让程序不崩」，而是「让每一种错误都被正确的人看到」。** 用户输错了告诉用户，程序写错了告诉开发者——`try` 包得太大、`except` 写得太宽，都会让这两件事混在一起。

<details>
<summary>参考答案</summary>

1. **类型**（哪一类问题）、**消息**（具体细节）、**traceback**（从哪一行、经过哪些调用来的）、**传播**（沿调用链向上，直到有人处理）。
2. 调用方很容易**忘记检查**，错误值被当成正常值继续用，静默算出错误结果。异常的好处是**不处理就会炸**，你忘了处理，程序会停下来告诉你。
3. 分别是 `ValueError` 和 `TypeError`。**类型对但值不行是 `ValueError`**（字符串能转整数，只是 `"abc"` 这个内容不行）；**类型本身就不对是 `TypeError`**（`None` 根本不是 `int()` 能接受的类型）。
4. **不会。** 异常一抛出，`try` 块剩余的部分全部跳过，直接去找匹配的 `except`。
5. `trace("42")` → `["try", "else", "finally"]`；`trace("abc")` → `["try", "except", "finally"]`。
6. **不能。** `except` 块结束后 Python 会自动删除 `e`。在函数里访问会报 `cannot access local variable 'e'...`，在模块顶层会报 `name 'e' is not defined`。要在块外用，得在块内先赋给别的变量。
7. 裸 `except:` 会接住**所有**异常，包括 `SystemExit` 和 `KeyboardInterrupt`；`except Exception:` 不接这两个。不能写裸 `except` 是因为它会让 **Ctrl+C 失效、`sys.exit()` 不退出**。
8. 都继承自 **`BaseException`**。`Exception` 也是 `BaseException` 的子类，三者是兄弟关系，所以 `except Exception` 接不住前两个。
9. `try` **没有**抛出任何异常时执行。用途是把「成功后才该做的事」从 `try` 里拿出来，**让 `try` 尽量小**，避免误捕获。
10. **会。** `finally` 在函数真正返回之前执行。
11. 一是**覆盖 `try` 的返回值**（`try` 里 `return 1`、`finally` 里 `return 2`，结果是 2）；二是**吞掉异常**（`try` 里抛出的异常静默消失）。**第二个更危险**，错误消失得没有任何痕迹。
12. **LBYL** = 先检查再行动，如 `if looks_like_int(raw): int(raw)`；**EAFP** = 先做再处理失败，如 `try: int(raw) except ValueError: ...`。
13. 因为 EAFP 的**判断标准就是 `int()` 本身**。LBYL 是自己写一套检查规则去模仿 `int()`，每条规则都可能漏——比如下划线 `1_000`，以及它的各种非法写法 `1__000`、`_1`。
14. **Time Of Check to Time Of Use**：检查和使用之间有时间差，状态可能在这期间变化（比如检查时文件存在，打开时已被删除）。LBYL 的检查结果在使用时可能已经失效；EAFP 直接操作，失败了处理，没有这个时间差。
15. 因为 `raw` 声明的类型是 `str`，传 `None` 进来是**调用方写错了**，应该让 `TypeError` 暴露出来。捕获它会把「用户输错了」和「程序写错了」混成一回事。
16. 返回 `"输入无效"`。问题在于这是**配置写错了**（程序的 bug），却被伪装成用户输入有问题——用户怎么改输入都没用，开发者也不会想到去查配置。判断标准：**这个 `except` 准备处理哪一种失败，就只把会产生这种失败的代码放进 `try`。**
17. 「是不是整数」的规则是 **`int()` 定义的**，自己写容易和它不一致，所以交给 `int()` 判断（EAFP）；「在不在 1-100」是**自己定义的业务规则**，不存在「和谁不一致」的问题，检查成本也极低，用 LBYL 最直接。

# 一、概念与原理

## 1. 自动化测试是什么

把「什么输入应该得到什么输出」写成代码，一条命令跑完全部。

```python
# 手动测试：运行程序，输入 30，看屏幕上是不是「小了」
# 自动化测试：
assert check_num(30, 50) == "小了"
```

核心价值是**一次写、无限次跑**。写测试的成本是一次性的，收益随代码修改次数累积。

这一章用最原始的工具 `assert` 入门。第 2.3 章会换成 `pytest`——但先理解 `assert`，因为 `pytest` 的断言底层就是它。

## 2. `assert` 的语义

```python
assert 表达式
assert 表达式, "失败时的提示信息"
```

读作「**我断定这个表达式为真**」：

| 表达式求值结果 | 发生什么 |
|---|---|
| 真 | 什么都不发生，程序继续 |
| 假 | 抛出 `AssertionError`，程序停在这一行 |

```python
assert check_num(30, 50) == "小了"      # 通过，无输出
assert check_num(30, 50) == "大了"      # AssertionError
```

**一串 `assert` 全部通过时没有任何输出。** 这是正常的，不是「没跑」：

```text
（全部通过时，终端上什么都不会出现）
```

初学时很容易因为看不到输出而怀疑测试没执行。记住：**沉默就是通过。**

## 3. 断言失败长什么样

两种写法的报错信息差别很大：

```python
# 不带消息
assert check_num(30, 50) == "大了"
```

```text
AssertionError, args=()
```

**异常里什么信息都没有。** 你只知道「某一行断言失败了」，不知道实际值是什么。

```python
# 带消息
result = check_num(30, 50)
expected = "大了"
assert result == expected, f"预期 {expected}，实际得到 {result}"
```

```text
AssertionError: 预期 大了，实际得到 小了
```

**一眼看出问题。** 逗号后面的内容会成为 `AssertionError` 的参数。

**惯例**：简单的、一眼能看懂的断言可以不写消息；涉及计算结果、循环里的多次断言、或者失败后需要知道具体数值的，都应该带上消息。

### 一个会让你困惑的差异：pytest 里不是这样

上面「不带消息就什么信息都没有」的结论，**只在直接用 `python` 运行时成立**。

同一条断言放进 `pytest` 跑，失败信息是这样的：

```text
>       assert example.check_num(30, 50) == "大了"
E       assert '小了' == '大了'
E
E         - 大了
E         + 小了
```

**两边的值都打出来了，而且标出了差异。** 但代码里一个字的消息都没写。

原因是 `pytest` 做了一件叫**断言重写（assertion rewriting）**的事：它在导入测试模块时改写字节码，把每个 `assert` 换成「失败时先把两边的值算出来、拼成详细信息、再抛异常」的版本。

可以直接验证这件事：

```python
with pytest.raises(AssertionError) as caught:
    assert check_num(30, 50) == "大了"

print(caught.value.args)
```

| 运行环境 | `AssertionError.args` |
|---|---|
| `python script.py` | `()` ——空的 |
| `pytest` | `("assert '小了' == '大了'\n\n  - 大了\n  + 小了",)` |

**同一行代码，异常内容不同。**

> 两个实际影响：
>
> 1. **用了 `pytest` 之后可以少写断言消息**，框架会自动补。写消息的价值变成「补充业务含义」
>    （比如 `"2024 应该是闰年"`），而不是「打印实际值」。
> 2. **别指望 `AssertionError.args` 是稳定的**。它的内容取决于谁在跑你的代码。
>    如果有逻辑依赖异常内容，应该自己 `raise` 一个带明确信息的异常，而不是靠 `assert`。
>
> 断言重写只对 `pytest` **收集到的测试文件**生效。被测代码里的 `assert`（比如业务模块里的）
> 不会被改写——这也是配套测试里那条验证必须开子进程的原因。

## 4. ⚠️ `assert` 在 `python -O` 下会被完全移除

这是这一章最重要的一条，也是最容易造成生产事故的一条。

```bash
python -O script.py
```

`-O`（optimize）模式下，**Python 的编译器会把所有 `assert` 语句直接删掉**，就像它们从没写过。

### 字节码证据

拿这个函数做实验：

```python
def parse_age(s: str) -> int:
    age = int(s)
    assert 0 <= age <= 150, "年龄不合法"
    return age
```

用 `dis` 模块看它编译成了什么指令：

```python
import dis
for ins in dis.get_instructions(parse_age):
    print(ins.opname)
```

**普通模式**（`python`）：

```text
当前 __debug__ = True
当前优化级别 sys.flags.optimize = 0

parse_age 的字节码里和 assert 有关的指令：
    50 LOAD_ASSERTION_ERROR
    62 RAISE_VARARGS
    66 LOAD_ASSERTION_ERROR
    78 RAISE_VARARGS
```

**优化模式**（`python -O`）：

```text
当前 __debug__ = False
当前优化级别 sys.flags.optimize = 1

parse_age 的字节码里和 assert 有关的指令：
  （没有任何 assert 相关指令 —— assert 已被编译器移除）
```

**不是「跳过不执行」，是指令根本不存在。** 这是编译期行为，运行时无法开关。

### 后果有多严重：两种校验的实测对比

配套代码里有两个版本的年龄校验，一个用 `assert`、一个用 `raise`。给它们同一个非法输入 `"200"`：

**普通模式**（`python -m m02_testing.ch02_01_example`）：

```text
6. 两种校验在当前模式下的表现
   parse_age_wrong (assert): 拦住了，AssertionError: 年龄不合法
   parse_age_right (raise) : 拦住了，ValueError: 年龄不合法：200
```

两个都拦住了。开发时测不出任何区别。

**优化模式**（`python -O -m m02_testing.ch02_01_example`）：

```text
6. 两种校验在当前模式下的表现
   parse_age_wrong (assert): 没有拦住，返回了 200  ← 校验失效
   parse_age_right (raise) : 拦住了，ValueError: 年龄不合法：200
```

**`assert` 版本把 200 岁原样放了过去。**

同一份代码还有另一处差异。示例第 1 节是这样写的：

```python
try:
    assert check_num(30, 50) == "大了"
except AssertionError as e:
    print(f"不带消息: AssertionError, args={e.args!r}")
```

| 运行方式 | 第 1 节的输出 |
|---|---|
| `python -m ...` | `不带消息: AssertionError, args=()` |
| `python -O -m ...` | **（整节什么都没有）** |

`assert` 被删了 → 没有异常抛出 → `except` 分支不执行 → **程序静默继续往下走**。

**这就是它危险的地方：没有报错、没有警告、没有日志，只是校验悄悄不生效了。**

### 由此得出的硬性规则

> **`assert` 只能用于测试代码和内部不变量检查，绝不能用于生产代码的输入校验。**

```python
# ✗ 错误：用 assert 校验外部输入
def parse_age(s: str) -> int:
    age = int(s)
    assert 0 <= age <= 150, "年龄不合法"      # -O 模式下这行消失，校验失效
    return age

# ✓ 正确：用 raise
def parse_age(s: str) -> int:
    age = int(s)
    if not 0 <= age <= 150:
        raise ValueError(f"年龄不合法：{age}")
    return age
```

判断标准：

| 用途 | 该用什么 | 理由 |
|---|---|---|
| 测试代码里验证预期 | `assert` | 测试永远不会用 `-O` 跑 |
| 检查「这里绝不可能发生」的内部不变量 | `assert` | 它本来就是开发期的自检 |
| **校验外部输入**（用户、文件、API、环境变量） | **`raise`** | **外部输入在生产环境也必须校验** |

`raise` 是第 2.2 章的内容。现在只需要记住这条分界。

> **`__debug__` 这个内置变量**就是 `-O` 的开关：普通模式为 `True`，`-O` 下为 `False`。
> `assert X` 在语义上等价于 `if __debug__: if not X: raise AssertionError`。
> 需要「`-O` 下也要生效的自检」时，可以显式写 `if not X: raise ...`。

## 5. 恒为真的断言

```python
assert check_num(30, 50)                  # ← 永远通过
assert check_num(30, 50) == "小了"        # ← 真正的断言
```

第一行**永远不会失败**，因为 `check_num` 返回的任何非空字符串都是真值：

```text
bool('小了') = True
bool('正确') = True
bool('大了') = True
→ assert check_num(...) 只要返回非空字符串就通过，和内容无关
```

即使函数的逻辑完全写反，这个断言照样通过。**写了等于没写。**

同类的坑：

```python
assert items                   # 只验证了「非空」，没验证内容
assert len(items) == 3         # 只验证了长度，没验证元素对不对
assert result is not None      # 只验证了「有返回值」
```

这些断言不是没用（它们能挡住返回 `None` 这类低级错误），但**不能用它们代替对内容的验证**。

> **自查方法**：写完一条断言，问一句「**有没有可能让它失败**」。
> 想不出任何输入能让它失败，这条断言就是无效的。

## 6. 测试函数的组织

```python
def test_check_num() -> None:
    assert check_num(30, 50) == "小了"
    assert check_num(50, 50) == "正确"
    assert check_num(70, 50) == "大了"
```

三条惯例：

### 一、函数名以 `test_` 开头

这不是语法要求，而是**测试框架的发现约定**。`pytest` 会自动找出所有 `test_` 开头的函数来执行（第 2.3 章）。现在就遵守，以后接框架不用改名。

### 二、测试函数里不要有 `input()` 和 `print()`

| | 为什么不能有 |
|---|---|
| `input()` | 会让测试卡住等人输入，自动化就谈不上了 |
| `print()` | 干扰输出，而且报告结果应该靠断言失败时的异常，不是靠打印 |

### 三、定义了测试函数，必须调用它

```python
def test_check_num() -> None:
    assert ...

test_check_num()               # ← 没有这一行，上面的断言一次都不会执行
print("所有测试通过！")          # 这个 print 放在测试函数外面
```

`def` 只是定义（第 1.6 章讲过），不调用就不执行。实测一下忘记调用会怎样：

```text
test_never_called 已定义，但没有调用。程序继续运行，没有任何提示。
函数对象存在吗： True
```

**哪怕函数里写着 `assert 1 == 2`，不调用也不会报错。** 这是「假测试」的第一种形态——测试存在，但从未运行。

> 交给 `pytest` 之后框架会自动调用，但在只用 `assert` 的阶段必须手动调。
> 第 2.3 章会看到这个坑的第二种形态：**用了 pytest，但测试写在 `if __name__ == "__main__"` 里，
> `pytest` 输出 `collected 0 items`**——同样是一次都没跑过。

## 7. 该测什么：三类输入

写测试时很容易只测「正常情况」，但 bug 大多藏在另外两类。

针对 `check_num(input_num, target_num)`：

| 类型 | 用例 | 考察什么 |
|---|---|---|
| **正常值** | `(30, 50)`、`(70, 50)` | 典型的小于、大于 |
| **边界值** | `(50, 50)` 相等、`(1, 100)` 最小、`(100, 1)` 最大 | `<` 和 `<=` 的分界 |
| **异常值** | 非整数、`None`、超范围 | 错误处理 |

**边界值最容易出错**，因为它们正好落在比较运算符的分界上。一个实用的检查清单：

- 相等的情况测了吗？
- 最小值、最大值测了吗？
- 空集合（`[]`、`""`、`{}`）测了吗？
- 刚好超出范围一点（范围是 1-100 就试 `0` 和 `101`）测了吗？

> 第 1.9 章那个「`0` 被当成合法输入放过去」的 bug，就是漏了边界值。

## 8. 验证测试本身有效：故意改错代码

**一个永远不会失败的测试，和没有测试是一样的。**

写完测试后应该做一次反向验证——**故意把被测代码改错**：

```python
def check_num(input_num: int, target_num: int) -> str:
    if input_num != target_num:        # 故意把 == 改成 !=
        return "正确"
    ...
```

再跑测试，**应该看到 `AssertionError`**。看到报错，才证明这套测试真的在起作用。然后把代码改回来。

这一步能发现三类问题：

| 问题 | 表现 |
|---|---|
| 断言写错了对象 | 改错代码后测试仍然通过 |
| 测试函数没被调用 | 改错代码后没有任何输出 |
| 断言条件恒为真（第 5 节） | 改错代码后测试仍然通过 |

**这是本章最该带走的一个习惯。** 它只花 30 秒，但能挡住「我以为我有测试」这类最危险的错觉。

## 9. 回归测试

上面那个「改错代码 → 测试报警」的过程，正是**回归测试**的原理：

> 以后修改代码时，已有的测试会告诉你有没有破坏旧功能。

「回归」指的是「功能退回到了错误状态」。这是测试最大的长期价值——**它让你敢改代码**。

| | 没有测试 | 有测试 |
|---|---|---|
| 改一处逻辑 | 担心影响到哪里，不敢动 | 跑一遍就知道 |
| 重构 | 基本不可能 | 常规操作 |
| 接手别人的代码 | 只能靠读 | 测试就是可执行的说明书 |

## 10. 可测试性来自设计

`check_num()` 之所以能三行测完，是因为它**只做一件事**：接收两个数字，返回一个字符串。

```python
assert check_num(30, 50) == "小了"       # 直接传参、直接断言返回值
```

它没有 `input()`、没有 `print()`、不碰随机数、不读文件。这种函数叫**纯函数**：

- 相同输入永远得到相同输出
- 不产生副作用（不修改外部状态、不做 IO）

**纯函数是最容易测试的代码。**

反过来，看一个难测的版本：

```python
def play_round(target: int) -> None:          # 返回 None
    guess = int(input("请输入："))              # 依赖键盘输入
    if guess == target:
        print("正确")                          # 结果只在屏幕上
    elif guess < target:
        print("小了")
    else:
        print("大了")
```

想测它，得模拟键盘输入、捕获标准输出——要用到第 8.1 章的 Mock 才做得到。而拆成「纯逻辑 + 薄壳」之后，核心逻辑三行就测完了：

```python
def check_num(input_num: int, target_num: int) -> str:    # 纯函数，好测
    ...

def play_round(target: int) -> None:                      # 薄壳，几乎没有逻辑
    guess = int(input("请输入："))
    print(check_num(guess, target))
```

> **测试写不出来，往往不是测试技术的问题，而是被测代码的结构有问题。**
>
> 这条规律贯穿整门课。第 7.2 章把 `APIClient` 拆成三层、第 8.1 章能用 Mock 隔离网络，
> 前提都是「逻辑和 IO 分开了」。

## 11. 测试代码也要能被读懂

测试是一种文档——它说明了「这个函数应该怎么表现」。所以测试本身也该清楚：

```python
# ✗ 看不出在测什么
assert f(1, 2) == 3

# ✓ 意图明确
def test_猜小了时返回提示():
    assert check_num(30, 50) == "小了"
```

常见结构是「**一个测试函数只测一个场景**」，函数名直接说明场景。这样测试失败时，光看名字就知道哪个行为坏了，不用去读断言。

两种命名风格都常见：

| 风格 | 例子 |
|---|---|
| 中文描述 | `def test_猜小了时返回提示()` |
| `test_被测对象_场景_预期` | `def test_check_num_input_less_than_target()` |

团队内统一就行。本章先把三个场景写在一个函数里，第 8.2 章学完 `pytest` 再拆开。

def is_leap_year(year: int) -> bool:

## 练习 2（基础）· 找出三条无效断言

`exercise.py` 里有一个 `test_broken()` 函数，里面三条断言都有问题：

```python
def test_broken() -> None:
    assert is_leap_year(2024)                      # 问题 1
    assert is_leap_year(2023) == False or True     # 问题 2
    assert len(str(is_leap_year(2024))) == 4       # 问题 3
```

**要求**：

1. 在注释里写出每一条的问题是什么

# 三、常见错误

这一章对应的错误模式，完整版会收进附录 A 常见错误手册（编写中）。

| # | 错误 | 表现 | 怎么避免 |
|---|---|---|---|
| **A-1** | **定义了测试函数但没调用** | 没有任何输出，看起来像「全部通过」 | 文件末尾检查每个 `test_` 函数都被调用；或者直接用 `pytest` |
| **A-2** | **断言条件恒为真** | 改错被测代码，测试照样通过 | 写完问「有没有可能让它失败」 |
| **A-3** | **用 `assert` 校验外部输入** | 开发环境正常，`-O` 跑的生产环境校验全部失效 | 外部输入一律用 `raise` |
| **A-4** | **预期异常没发生时静默通过** | `try/except` 包住的断言，异常没抛出时测试也不失败 | 用 `pytest.raises()`（第 2.3 章） |
| **A-5** | **只测正常值** | 上线后被 `0`、空列表、刚好超范围的输入打挂 | 按第 7 节的清单逐项检查 |

**A-3 和 A-1 这两条都来自真实案例**，而且都有一个共同点：**不报错、不警告，程序照常运行**。附录 A 里有完整的复现步骤。

# 四、本章小结

```text
手动测试的三个失效点
    ↓
assert：沉默是通过，失败抛 AssertionError
    ↓
⚠️ -O 会删掉 assert  →  外部输入必须用 raise
    ↓
三类输入：正常值 / 边界值 / 异常值
    ↓
故意改错代码，验证测试有效  ←  本章最该带走的习惯
    ↓
可测试性来自设计：纯函数最好测
```

一句话总结：**写测试的目的不是「有测试」，而是「测试能在代码坏掉的时候告诉你」。** 这两件事差别很大，区分它们的唯一办法是故意把代码改错。

<summary>参考答案</summary>

1. **什么都不输出。** 沉默就是通过。初学时容易因此怀疑测试没执行。
2. 不带消息时异常里没有任何信息（`args=()`），只知道「某行断言失败了」；带消息时消息成为 `AssertionError` 的参数，能直接看到实际值和预期值。
3. **把 `assert` 语句从字节码里完全删除**，不是跳过执行——指令根本不存在。这是编译期行为。证明方法：用 `dis.get_instructions()` 看函数字节码，普通模式下有 `LOAD_ASSERTION_ERROR` 和 `RAISE_VARARGS`，`-O` 模式下这些指令消失。
4. 普通模式 `True`，`-O` 模式 `False`。`assert X` 在语义上等价于 `if __debug__: if not X: raise AssertionError`。
5. 因为生产环境可能用 `-O` 运行，那时 `assert` 被删除，**校验静默失效**。该用 `raise`（配合 `if not 条件:`）。
6. 它**恒为真**——`check_num` 返回的任何非空字符串都是真值（`bool('小了')` 为 `True`），所以函数逻辑完全写反它也通过。**只有在函数返回空字符串或 `None` 时才会失败**，而那不是这条断言想验证的东西。
7. 问「**有没有可能让它失败**」。想不出任何输入能让它失败，这条断言就是无效的。
8. 因为这是**测试框架的发现约定**（`pytest` 自动收集 `test_` 开头的函数）。不是语法要求，但遵守它以后接框架不用改名。
9. `input()` 会让测试卡住等人输入，自动化就不成立；`print()` 干扰输出，而且报告结果应该靠断言失败抛出的异常，不是靠打印。
10. **什么都不会发生，程序正常结束，没有任何提示。** `def` 只是定义，不调用就不执行。这是「假测试」的第一种形态：测试存在但从未运行。
11. **正常值、边界值、异常值。边界值最容易出错**，因为它们正好落在 `<` 和 `<=` 的分界上（相等、最小值、最大值、空集合、刚好超范围）。
12. **故意把被测代码改错，确认测试报错。** 能发现三类问题：断言写错了对象、测试函数没被调用、断言条件恒为真。三者的共同表现都是「改错代码后测试仍然通过或仍然没有输出」。
13. 修改代码时，已有的测试会告诉你有没有破坏旧功能（「回归」= 功能退回到错误状态）。最大的价值是**让你敢改代码**——没有测试时改一处要担心影响到哪里，有测试时跑一遍就知道。
14. 相同输入永远得到相同输出、不产生副作用（不修改外部状态、不做 IO）的函数。好测是因为可以**直接传参、直接断言返回值**，不需要模拟环境。
15. 因为它**依赖键盘输入**（要模拟 `input()`）、**结果只在屏幕上**（要捕获标准输出）、**返回 `None`**（没有可断言的值）。改法是拆成「纯函数 + 薄壳」：把判断逻辑提成返回字符串的纯函数，外层函数只负责 `input()` 和 `print()`，自己几乎没有逻辑。

# Day 8：不启动游戏，也能知道函数对不对

到现在为止，你检查代码的办法一直是：运行游戏，手敲几个数，看提示对不对。昨天交作业前，你要试直接 `q`、试 `abc`、试 `0`、试 `101`、再正常猜一次，一共五六种情况。

每改一次代码，这些都得重新敲一遍。改的是 A，你多半只会去试 A，B 坏了也不知道。

今天学**用代码检查代码**：把「什么输入应该得到什么结果」写下来，一运行就全部检查完。

## 一、`assert`：我断定这件事成立

```python
assert 1 + 1 == 2
assert 1 + 1 == 3
```

`assert` 后面跟一个条件：

- 条件成立，什么都不发生，接着往下执行
- 条件不成立，抛出 `AssertionError`，程序停在这一行

第一行成立，**没有任何输出**。这很正常，不是没运行。第二行不成立，就会报 `AssertionError`。

拿 Day 7 的 `check_num()` 来写：

```python
assert check_num(30, 50) == "小了"
assert check_num(50, 50) == "正确"
assert check_num(70, 50) == "大了"
```

三行把函数的三个分支都检查了一遍，不用随机数，不用 `input()`。

能这么写，是因为 Day 5 做对了一件事：`check_num()` 只接收两个数、交回一个结果，不打印、不读输入。这样的函数，直接传参、直接比较返回值就能检查。

## 二、把检查装进一个测试函数

一般会把这些 `assert` 放进一个以 `test_` 开头的函数：

```python
def test_check_num() -> None:
    assert check_num(30, 50) == "小了"
    assert check_num(50, 50) == "正确"
    assert check_num(70, 50) == "大了"


test_check_num()
print("所有测试通过！")
```

两点要记住：

1. **定义了，还要调用。** Day 5 讲过，`def` 只是把函数造出来，里面的代码要等调用时才执行。没有 `test_check_num()` 这一行，里面的 `assert` 一条都不会跑
2. **测试函数里不要有 `input()` 和 `print()`。** `input()` 会让测试停下来等人敲键盘，就不是自动的了。测试通没通过，看有没有抛 `AssertionError`，不靠打印。最后那句「所有测试通过」写在函数外面

名字用 `test_` 开头，是为了以后交给测试工具 pytest，它靠这个前缀找到测试函数。

## 三、测哪些值

只测 `30` 和 `50` 这种「随便挑的」数不够。错误最常出在**边界**上，比如 Day 7 的 0：

| 类型 | 例子 |
|---|---|
| 普通情况 | `(30, 50)` 小了，`(70, 50)` 大了 |
| 相等 | `(50, 50)` 正确 |
| 边界 | `(1, 100)`、`(100, 1)`、`(1, 1)`、`(100, 100)` |

## 四、确认测试真的能发现错误

测试写完全部通过，还不能说明什么。一个永远不会失败的测试，和没写一样。

检查办法是**故意把函数改坏**，看测试能不能抓住。把 `check_num()` 里的 `==` 改成 `!=`：

```python
def check_num(input_num: int, target_num: int) -> str:
    if input_num != target_num:      # 故意改错
        return "正确"
    ...
```

再运行测试，报错的最后几行是：

```text
    assert check_num(30, 50) == "小了"
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError
```

测试在第一条就抓住了。确认完记得改回来。

这一步还能揪出写错的测试。比如漏写了 `== "小了"`：

```python
assert check_num(30, 50)
```

函数已经改坏了，`check_num(30, 50)` 返回的是 `"正确"`，可这一行照样通过。因为它只检查「返回值是不是真」，而任何非空字符串都算真。这种断言什么都没测。

失败时想看到更多信息，可以在逗号后面写一句说明：

```python
assert result == "小了", f"预期 小了，实际得到 {result}"
```

```text
AssertionError: 预期 小了，实际得到 正确
```

以后改代码，先跑一遍测试，旧功能有没有被改坏一下就知道了。这叫**回归测试**，它让你敢改代码。

## 六、小测

**1.** 一串 `assert` 全部通过时，屏幕上会显示什么？

- A. 每条显示一个 True
- B. 什么都不显示
- C. 显示「测试通过」

**2.** `check_num` 返回 `"大了"` 时，`assert check_num(30, 50)` 会怎样？

- A. 通过
- B. 报 `AssertionError`

**3.** 文件里只有 `def test_check_num(): ...`，没有调用它。运行这个文件会怎样？

- A. 自动执行所有测试
- B. 什么都不执行，也不报错

<details>
<summary>答案</summary>

1. B。成立的 `assert` 不产生任何输出。
2. A。`"大了"` 是非空字符串，算作真。这个断言只检查了「有返回值」，没检查返回的对不对。
3. B。`def` 只定义函数，不调用就不执行。

</details>

## 讲评（10-21）

你交的代码：

```python
def check_num(input_num: int, target_num: int) -> str:
    if input_num == target_num:
        return "正确"
    elif input_num < target_num:
        return "小了"
    else:
        return "大了"

def test_check_num() -> None:
    assert check_num(30, 50) == "小了"
    assert check_num(50, 50) == "正确"
    assert check_num(70, 50) == "大了"
    assert check_num(1, 100) == "小了"
    assert check_num(100, 1) == "大了"
```

五条断言都写对了，每一条都比较了具体的返回值，三个分支和 1、100 两个边界都有。测试函数里没有 `input()` 和 `print()`。

缺的正是第二节说的那一行：**没有调用 `test_check_num()`。** 讲评里提醒过要补上，还要故意改错验证一次，你回了一句「好的进入第九天吧」，这两步就没做，`Day7.py` 一直是现在这个样子。

我实际跑了一下，问题比看上去严重：

- 直接运行 `Day7.py`：没有任何输出，正常结束
- 把 `==` 改成 `!=` 再运行：**还是没有任何输出，还是正常结束**

函数已经错了，文件却一声不吭。原因很简单，五条 `assert` 一条都没执行过。从外面看，「测试全部通过」和「测试根本没跑」长得一模一样，都是什么都不显示。

在文件末尾补上两行：

```python
test_check_num()
print("所有测试通过！")
```

再运行，正确的版本会打印「所有测试通过！」，改坏的版本会在第一条断言处报 `AssertionError`，这时候测试才算真的在工作。

这也是第四节那一步为什么不能省：**让测试失败一次，你才知道它真的会失败。** 当时如果做了这一步，马上就会发现改坏了也没反应，没调用的问题自然就暴露了。

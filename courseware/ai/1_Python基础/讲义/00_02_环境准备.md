# 0.2 环境准备

> **前置** 0.1 这门课怎么学
> **时长** 约 60 分钟（全部动手）
> **配套代码** [`code/m00_setup/`](../../code/m00_setup/)

这一章**必须做完**，后面 32 章的代码都依赖它。做完会有一个自检脚本告诉你配置对不对。

## 学习目标

1. 说清**为什么**每个项目都要有自己的虚拟环境，而不是把包装到系统 Python 里
2. 创建、激活虚拟环境，并用两种方法**验证自己真的在虚拟环境里**
3. 看懂 `.venv/` 目录里有什么，`pyvenv.cfg` 的 `include-system-site-packages` 管什么
4. 解决 Windows 下的三个常见障碍：WindowsApps 占位符、PowerShell 执行策略、中文乱码
5. 用 `pyproject.toml` 声明依赖，并说明 `pip install -e` 的 `-e` 是什么意思
6. 跑通 `pytest` / `ruff` / `mypy` 三个工具

# 一、为什么需要虚拟环境

## 1. 先看一台真实机器上的情况

```powershell
py -0p
```

```text
 -V:3.13 *        D:\Program Files\python3000\python.exe
 -V:3.11          C:\Users\hubo\AppData\Local\Programs\Python\Python311\python.exe
 -V:2.7           C:\Python27\python.exe
 -V:Astral/CPython3.12.13 C:/Users/hubo/.kiro/crew-python\cpython-3.12.13-...\python.exe
```

**四个 Python。** 这不是刻意安排的，是正常使用几年之后的自然状态：装过 2.7、后来装了 3.11、又升到 3.13，某个工具自带了 3.12。

现在问题来了：你 `pip install requests` 装到了哪一个里面？

## 2. 把包装进系统 Python 的三个后果

| 问题 | 具体表现 |
|---|---|
| **版本冲突** | 项目 A 要 `requests==2.28`，项目 B 要 `requests>=2.32`。装了一个，另一个坏 |
| **说不清依赖** | 系统里装了 80 个包，你的项目到底用了哪 5 个？别人怎么复现 |
| **卸不干净** | 想删掉某个项目的依赖，但不知道哪些包是它带进来的 |

**虚拟环境的作用就是给每个项目一个独立的包目录。**

```text
系统 Python  ────┬──→  项目 A 的 .venv/   requests 2.28, flask
                 ├──→  项目 B 的 .venv/   requests 2.32, django
                 └──→  这门课的 .venv/    requests 2.32, pytest, ruff, mypy
```

三个环境互不影响。删掉 `.venv/` 目录，这个项目的依赖就彻底消失了，系统干干净净。

> **这是 Python 的硬性最佳实践，不是可选项。** 任何一份 Python 项目文档，
> 第一步都是「创建虚拟环境」。

# 二、第一步：确认 Python 版本

```powershell
python --version
```

```text
Python 3.13.2
```

**这门课要求 Python 3.10 或更高**（用到了 `X | Y` 类型联合语法，3.10 才支持）。

版本不够或者没装，去 [python.org/downloads](https://www.python.org/downloads/) 装一个。**安装时勾上 "Add Python to PATH"**，不然命令行里敲 `python` 找不到。

## Windows 陷阱一：WindowsApps 占位符

```powershell
where.exe python
```

```text
D:\Program Files\python3000\python.exe
C:\Users\hubo\AppData\Local\Microsoft\WindowsApps\python.exe
```

**第二条是个假的。** 它是微软放的占位符，作用是在你没装 Python 时打开应用商店。

如果你敲 `python` 弹出了微软商店，或者报「找不到 Python，可从 Microsoft Store 安装」，就是这个占位符抢在了真 Python 前面。两个解法：

| 解法 | 做法 |
|---|---|
| **推荐** | 用 `py` 代替 `python`（`py` 是 Python 官方启动器，不受影响） |
| 彻底 | 设置 → 应用 → 高级应用设置 → 应用执行别名 → 关掉 "python.exe" 和 "python3.exe" |

## Windows 陷阱二：装了多个版本，不确定用的是哪个

`py` 启动器可以指定版本：

```powershell
py -0p              # 列出所有版本（上面那个输出）
py -3.11 --version  # 用 3.11
py -3.13 --version  # 用 3.13
py --version        # 用默认的（上面带 * 的那个）
```

**建虚拟环境时用哪个 `python`，这个虚拟环境就锁定哪个版本。** 所以如果系统默认版本不对，建环境时要显式指定：

```powershell
py -3.13 -m venv .venv
```

# 三、第二步：创建虚拟环境

进到课程代码目录，执行：

```powershell
cd code
python -m venv .venv
```

没有任何输出就是成功了（退出码 0）。这一步大约 5 秒。

> **为什么是 `python -m venv` 而不是 `venv`？**
> `-m` 的意思是「把 venv 当模块运行」。这样用的一定是**当前这个 `python`** 自带的 venv，
> 不会出现「命令找到的是另一个版本」的问题。第 3.1 章会详细讲 `-m`。

## 虚拟环境到底是什么

它就是一个目录。看看里面有什么：

```powershell
Get-ChildItem .venv
```

```text
Mode   Name
----   ----
d----- Include
d----- Lib              ← 装的包都在这里（Lib\site-packages）
d----- Scripts          ← 可执行文件（Windows；Linux/macOS 叫 bin）
-a---- .gitignore       ← venv 自己生成的，内容是 *
-a---- pyvenv.cfg       ← 配置文件
```

`Scripts` 目录里是这些：

```text
activate          ← 激活脚本（bash）
activate.bat      ← 激活脚本（cmd）
activate.fish     ← 激活脚本（fish）
Activate.ps1      ← 激活脚本（PowerShell）← Windows 用这个
deactivate.bat
pip.exe
pip3.13.exe
pip3.exe
python.exe        ← 这个虚拟环境的 python
pythonw.exe
```

**注意 `.venv\Scripts\python.exe`。** 它不是一份完整的 Python 拷贝（才几十 KB），而是一个指向系统 Python 的转发器，但它会把包的搜索路径指到 `.venv\Lib\site-packages`。

## `pyvenv.cfg`：隔离是怎么实现的

```powershell
Get-Content .venv\pyvenv.cfg
```

```text
home = D:\Program Files\python3000
include-system-site-packages = false
version = 3.13.2
executable = D:\Program Files\python3000\python.exe
command = D:\Program Files\python3000\python.exe -m venv C:\...\.venv
```

| 字段 | 作用 |
|---|---|
| `home` | 系统 Python 在哪（标准库从那里来） |
| **`include-system-site-packages = false`** | **关键**：不要去看系统装的包 |
| `version` | 锁定的 Python 版本 |

**隔离就是 `include-system-site-packages = false` 这一行做的。** 它让这个环境只看自己的 `site-packages`。

## 验证它是干净的

```powershell
pip list
```

```text
Package Version
------- -------
pip     24.3.1
```

**只有 `pip`。** 系统里装过多少包都不影响这里——这正是我们要的。

# 四、第三步：激活

| 平台 / Shell | 命令 |
|---|---|
| **Windows PowerShell** | `.\.venv\Scripts\Activate.ps1` |
| Windows cmd | `.venv\Scripts\activate.bat` |
| macOS / Linux | `source .venv/bin/activate` |

成功后命令提示符前面会多一个前缀：

```text
(.venv) PS D:\...\code>
```

## Windows 陷阱三：PowerShell 不让跑脚本

如果看到这个报错：

```text
无法加载文件 .venv\Scripts\Activate.ps1，因为在此系统上禁止运行脚本。
```

是 PowerShell 的**执行策略**挡住了。先看当前设置：

```powershell
Get-ExecutionPolicy -List
```

```text
        Scope ExecutionPolicy
        ----- ---------------
MachinePolicy       Undefined
   UserPolicy       Undefined
      Process       Undefined
  CurrentUser       Undefined
 LocalMachine    RemoteSigned
```

`RemoteSigned` 的含义是「本地写的脚本可以跑，从网上下载的必须有签名」。**这个设置下 `Activate.ps1` 能跑**，因为它是 venv 在本地生成的。

如果你的 `CurrentUser` 是 `Restricted`（禁止一切脚本），改成 `RemoteSigned`：

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

| 策略 | 含义 | 建议 |
|---|---|---|
| `Restricted` | 禁止所有脚本 | 太严，开发不方便 |
| **`RemoteSigned`** | 本地脚本可跑，下载的要签名 | **推荐** |
| `Unrestricted` | 全部允许 | 不安全，别用 |

> 只改 `CurrentUser` 作用域，不要改 `LocalMachine`——**改系统级设置需要管理员权限，
> 而且影响这台机器上的所有用户**。最小权限原则。

## 怎么确认真的激活了

提示符上的 `(.venv)` 可能骗人（有些终端配置会隐藏它）。有两个可靠方法。

### 方法一：看 `sys.prefix`

**激活前：**

```text
sys.prefix     = D:\Program Files\python3000
sys.executable = D:\Program Files\python3000\python.exe
VIRTUAL_ENV    = ''
```

**激活后：**

```text
sys.prefix     = C:\...\pe-course-lab\.venv
sys.executable = C:\...\pe-course-lab\.venv\Scripts\python.exe
VIRTUAL_ENV    = 'C:\...\pe-course-lab\.venv'
sys.base_prefix= D:\Program Files\python3000
```

| 变量 | 激活前 | 激活后 |
|---|---|---|
| `sys.prefix` | 系统 Python | **虚拟环境** |
| `sys.base_prefix` | 系统 Python | 系统 Python（不变） |
| `VIRTUAL_ENV` | 空 | 虚拟环境路径 |

### 方法二：一行判断（推荐）

```powershell
python -c "import sys; print('在虚拟环境里:', sys.prefix != sys.base_prefix)"
```

```text
在虚拟环境里: True
```

**`sys.prefix != sys.base_prefix` 是判断是否在虚拟环境里的标准方法。** 激活前跑同一条命令会得到 `False`。

> 为什么不用 `VIRTUAL_ENV` 这个环境变量？因为它只在用激活脚本时才会设置。
> 直接调用 `.venv\Scripts\python.exe`（不激活）也能用虚拟环境，但那时 `VIRTUAL_ENV` 是空的。
> `sys.prefix` 的判断在两种情况下都对。

## 退出虚拟环境

```powershell
deactivate
```

**关掉终端也等于退出。** 虚拟环境的激活只对当前这个终端有效，所以**每次开新终端都要重新激活**。

# 五、第四步：安装依赖

```powershell
pip install -e ".[dev]"
```

这条命令里有三个要解释的部分。

## `pyproject.toml`：依赖声明在哪

```toml
[project]
name = "python-engineering-course"
requires-python = ">=3.10"
dependencies = [
    "requests>=2.32",
    "python-dotenv>=1.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.3",
    "ruff>=0.8",
    "mypy>=1.13",
]
```

| 区块 | 装什么 | 什么时候需要 |
|---|---|---|
| `dependencies` | 运行必需 | 任何人跑这份代码都要 |
| `optional-dependencies.dev` | 开发工具 | 只有要跑测试、检查代码时才要 |

**分开声明的理由**：部署到生产环境时不该装 `pytest`。生产只要 `pip install .`，开发才 `pip install -e ".[dev]"`。

> `pyproject.toml` 是现在的标准做法（PEP 621）。
> 你可能见过 `requirements.txt`，那是更早的方式，只能列包名、不能声明项目元信息和可选分组。
> 新项目用 `pyproject.toml`。

## `-e` 是什么：可编辑安装

| 写法 | 效果 |
|---|---|
| `pip install .` | 把代码**拷贝**进 `site-packages`。改源码要重新装 |
| **`pip install -e .`** | 只放一个**指向源码目录的链接**。改源码立即生效 |

**开发时一律用 `-e`。** 否则每改一行代码都要重装一次。

## `".[dev]"` 的引号

```powershell
pip install -e ".[dev]"      # ✓ 带引号
pip install -e .[dev]        # ✗ 某些 shell 下会出错
```

`[` 和 `]` 在 PowerShell、zsh 里是通配符（glob）字符，不加引号会被 shell 先解释掉。**养成加引号的习惯。**

## 装完检查

```powershell
pip list
```

应该能看到 `requests`、`python-dotenv`、`pytest`、`ruff`、`mypy`，以及它们的依赖。

## 验证隔离真的生效了

在虚拟环境里装的包，系统 Python 看不到：

```powershell
python -c "import six; print(six.__file__)"
```

```text
C:\...\.venv\Lib\site-packages\six.py
```

**路径在 `.venv\Lib\site-packages` 里面。** 用系统 Python 跑同一行会得到 `ModuleNotFoundError`。

# 六、第五步：验证工具链

三个工具，各管一件事：

| 工具 | 管什么 | 命令 |
|---|---|---|
| **pytest** | 跑测试 | `pytest` |
| **ruff** | 代码风格 + 潜在错误 | `ruff check .` |
| **mypy** | 类型检查 | `mypy .` |

一条条试：

```powershell
pytest
```

```text
..........................sss..................................... [ 60%]
...........sssss.sss......................ssssssssss.ss            [100%]
N passed, M skipped in 2.1s
```

**具体数字会随你做到第几章而变化，只要没有 `failed` 就对了。** `skipped` 是正常的——那些是你还没做的练习，做完一道就少一个。

```powershell
ruff check .
```

```text
All checks passed!
```

```powershell
mypy .
```

```text
Success: no issues found in 4 source files
```

三条都对了，环境就配好了。

## 三个工具的配置都在 `pyproject.toml` 里

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff.lint]
select = ["F", "E", "W", "N", "UP", "SIM"]
ignore = ["E501"]

[tool.mypy]
disallow_untyped_defs = true
warn_return_any = true
warn_unused_ignores = true
no_implicit_optional = true
exclude = ['_exercise\.py$']
```

**每一项都带了注释说明为什么这么设**，建议打开看一眼。两处值得现在就知道：

**一、`mypy` 刻意没开 `strict = true`。** `strict` 会连带打开十几个开关，报错时分不清是哪条规则在管。这里逐条列出四个，第 1.6 章讲类型注解时会解释它们各自在查什么。

**二、练习文件被 `mypy` 排除了**（`exclude = ['_exercise\.py$']`）。它们是留给你填的，没写完时不该被类型检查拦住。

# 七、虚拟环境不要提交到仓库

`.venv/` 目录有几十到几百 MB，而且**里面的路径是绝对路径**，拷到别人机器上根本用不了。

好消息是 `venv` 自己就知道这件事：

```powershell
Get-Content .venv\.gitignore
```

```text
# Created by venv; see https://docs.python.org/3/library/venv.html
*
```

**`venv` 创建时自动在里面放了一个忽略一切的 `.gitignore`。** 这是官方表态：虚拟环境不该入库。

不过项目根目录的 `.gitignore` 仍然建议显式写上，加上工具缓存：

```gitignore
# 虚拟环境
.venv/
venv/

# Python 缓存
__pycache__/
*.py[cod]
*.egg-info/

# 工具缓存
.pytest_cache/
.ruff_cache/
.mypy_cache/
```

**该提交的是 `pyproject.toml`**——别人拿到它，`pip install -e ".[dev]"` 就能复现同样的环境。

> 「提交依赖声明，不提交依赖本身」是所有现代语言的通用做法：
> Python 的 `pyproject.toml`、Node 的 `package.json`、Rust 的 `Cargo.toml`。

# 八、Windows 用户：解决中文乱码

PowerShell 的默认控制台代码页是 **936（GBK）**，而 Python 输出的是 UTF-8。不处理的话，报错里的中文会变成这样：

```text
>       assert example.check_num(30, 50) == "澶т簡"
E       assert ("assert '灏忎簡'... 澶т簡\n  + 灏忎簡",) == ()
```

确认一下你的情况：

```powershell
chcp
```

```text
活动代码页: 936
```

**每次开新终端先执行这两行：**

```powershell
$env:PYTHONUTF8 = 1
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

想一劳永逸，写进 PowerShell 配置文件：

```powershell
notepad $PROFILE
```

> ⚠️ **`PYTHONUTF8=1` 有一个副作用，第 4.1 章会专门讲**：
> 它让 `open()` 默认用 UTF-8，从而**掩盖「忘记写 `encoding="utf-8"`」这个 bug**。
> 到那一章会要求你临时去掉这个设置来复现问题。
>
> 这是个典型的工程权衡：一个让开发体验变好的设置，同时降低了你发现某类 bug 的概率。

## 练习 2（基础）· 验证隔离

**要求**：用三条命令证明虚拟环境真的隔离了。

1. 激活虚拟环境，打印 `sys.prefix` 和 `sys.base_prefix`，确认两者**不同**
2. 执行 `deactivate`，再打印一次，确认两者**相同**
3. 重新激活，用 `pip list` 确认 `pytest` 在列表里；然后用系统 Python 的绝对路径执行
   `-c "import pytest"`，确认它**报 `ModuleNotFoundError`**（如果你的系统 Python 恰好装了 pytest，换一个只在课程里装的包试）

把三步的输出记下来。这是你以后遇到「包明明装了却导入不到」时的排查基线。

## 练习 3（进阶）· 故意制造一次导入失败

**要求**：

1. 在虚拟环境**激活的状态**下跑 `pytest`，确认通过
2. `deactivate`，再跑一次 `pytest`，观察发生了什么
3. 回答：报错信息是什么？从报错能看出是「没激活虚拟环境」吗？

> 这道题的意义：**`ModuleNotFoundError` 最常见的原因不是没装包，是装在了另一个环境里。**
> 以后遇到它，第一反应应该是检查 `sys.prefix`，而不是重新 `pip install`。

## 练习 4（进阶）· 读懂 `pyproject.toml`

打开 `code/pyproject.toml`，回答：

1. `dependencies` 和 `optional-dependencies.dev` 为什么要分开？部署到生产环境时该用哪条 pip 命令？
2. `[tool.ruff.lint]` 里的 `select = ["F", "E", "W", "N", "UP", "SIM"]` 各是什么含义？
   （提示：查 [ruff 规则文档](https://docs.astral.sh/ruff/rules/)，或者先猜，第 1.1 章会用到）
3. `exclude = ['_exercise\.py$']` 里的 `$` 是什么意思？去掉它会有什么区别？

# 十、常见错误

| # | 症状 | 原因 | 解决 |
|---|---|---|---|
| 1 | 敲 `python` 弹出微软商店 | WindowsApps 占位符抢了 PATH | 用 `py`，或关掉应用执行别名 |
| 2 | `Activate.ps1 ... 禁止运行脚本` | PowerShell 执行策略是 `Restricted` | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| 3 | `pip install -e .[dev]` 报错 | `[` `]` 被 shell 当通配符 | 加引号：`".[dev]"` |
| 4 | `ModuleNotFoundError: No module named 'pytest'` | **虚拟环境没激活** | 检查 `sys.prefix != sys.base_prefix` |
| 5 | 改了代码不生效 | 用了 `pip install .`（非 `-e`） | 重装成 `pip install -e .` |
| 6 | 报错里的中文是乱码 | 控制台代码页 936 | 设 `PYTHONUTF8=1` + `OutputEncoding` |
| 7 | 每开一个终端都要重新激活 | **这是正常的**，激活只对当前终端有效 | 写进终端配置，或用 IDE 的自动激活 |
| 8 | `pytest` 显示一堆 `skipped` | **这是正常的**，那些是没做的练习 | 做完练习就没有了 |

**第 4 条是整章最该记住的。** 它是 Python 新手最高频的报错，而「重新 pip install」通常解决不了——因为问题不是没装，是装在了别处。

# 十一、本章小结

```text
系统里有多个 Python  →  包装进系统会冲突
        ↓
python -m venv .venv          创建（一个目录）
        ↓
.\.venv\Scripts\Activate.ps1  激活（只对当前终端有效）
        ↓
sys.prefix != sys.base_prefix 验证（唯一可靠的判断方法）
        ↓
pip install -e ".[dev]"       装依赖（-e 可编辑，[dev] 开发工具）
        ↓
pytest / ruff / mypy          三个工具各管一件事
        ↓
.venv/ 不入库，pyproject.toml 入库
```

一句话总结：**虚拟环境不是「高级技巧」，它是 Python 项目的默认起点。** 任何一份不以它开头的 Python 教程，都跳过了最容易出问题的那一步。

1. 因为装过旧版本、后来升级、某些工具自带 Python，长期使用后自然会积累多个（实测一台机器上有 3.13、3.11、2.7 和一个工具自带的 3.12）。问题是**你不知道 `pip install` 装到了哪一个里面**。
2. 解决**依赖冲突、依赖说不清、卸不干净**三个问题。它本质上**就是一个目录**，里面有自己的 `site-packages` 和一个转发用的 `python.exe`。
3. `-m` 表示「把 venv 当模块运行」，用的一定是**当前这个 `python`** 自带的 venv，不会出现「命令找到的是另一个版本」的问题。
4. `Scripts`/`bin` 放可执行文件（激活脚本、`pip`、`python`）；`Lib\site-packages` 放安装的包。
5. `include-system-site-packages = false`。
6. **只有 `pip` 一个**。系统里装过多少包都不影响它。
7. `sys.prefix` 指向**虚拟环境目录**，`sys.base_prefix` 仍指向**系统 Python**（它记录的是「这个环境是基于哪个 Python 建的」）。
8. `sys.prefix != sys.base_prefix`。不用 `VIRTUAL_ENV` 是因为它**只在用激活脚本时才会设置**——直接调用 `.venv\Scripts\python.exe` 也能用虚拟环境，但那时 `VIRTUAL_ENV` 是空的，而 `sys.prefix` 的判断在两种情况下都对。
9. **算退出。** 激活只对当前终端有效，所以每次开新终端都要重新激活。
10. 微软放的**占位符**，作用是在没装 Python 时打开应用商店。绕开方法：用 `py` 启动器，或在「设置 → 应用 → 应用执行别名」里关掉它。
11. `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`。只改 `CurrentUser` 是因为**改系统级（`LocalMachine`）需要管理员权限，而且影响这台机器上的所有用户**——最小权限原则。
12. 因为**部署到生产环境时不该装 `pytest`**。生产用 `pip install .`，开发用 `pip install -e ".[dev]"`。
13. `pip install .` 把代码**拷贝**进 `site-packages`，改源码要重装；`-e` 是**可编辑安装**，只放一个指向源码目录的链接，改代码立即生效。**开发一律用 `-e`。**
14. 因为 `[` 和 `]` 在 PowerShell、zsh 里是**通配符字符**，不加引号会被 shell 先解释掉。
15. **不该。** 它有几十到几百 MB，而且里面是绝对路径，拷到别人机器上用不了。证据：**`venv` 创建时自动在 `.venv/` 里放了一个内容为 `*` 的 `.gitignore`**，这是官方表态。
16. 提交 **`pyproject.toml`**。别人拿到它执行 `pip install -e ".[dev]"` 就能复现同样的环境。这叫「提交依赖声明，不提交依赖本身」，Node 的 `package.json`、Rust 的 `Cargo.toml` 都是同一个思路。
17. 解决 Windows 控制台代码页 936（GBK）和 Python 的 UTF-8 输出不匹配造成的**中文乱码**。副作用是：它让 `open()` 默认用 UTF-8，从而**掩盖「忘记写 `encoding="utf-8"`」这个 bug**（第 4.1 章会复现）。
18. **检查虚拟环境有没有激活**（`sys.prefix != sys.base_prefix`）。这个报错最常见的原因不是没装包，而是**装在了另一个环境里**，所以重新 `pip install` 通常解决不了。

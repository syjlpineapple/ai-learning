# 3.3 项目分层与职责划分

> **前置** 3.2 类与面向对象
> **时长** 约 40 分钟
> **配套代码** [`code/m03_structure/guess/`](../../code/m03_structure/guess/)（拆分后的游戏）、[`ch03_03_example.py`](../../code/m03_structure/ch03_03_example.py)（分层检查）
> **对应学习记录** [Day10](../../../records/python/Day10.md)（三文件拆分）、[Day20](../../../records/python/Day20.md)（配置/客户端/入口三层）
>
> 从这一章起是**精简版**：只讲核心概念和踩过的坑，配套代码只有示例和验证结论的测试，不再配练习骨架。

## 要点

1. **按职责拆分**：规则（判断对错）、交互（问和说）、入口（组装和启动）各放一个模块
2. **依赖只能从上往下**：入口 → 交互 → 规则 → 异常。下层不知道上层的存在
3. **检验分层是否成立**，问三个问题：规则能不能不碰 `input`/`print` 就测试？换一种界面要改几个文件？有没有反向依赖？
4. `python -m 包名` 运行的是包里的 `__main__.py`；包的 `__init__.py` 保持为空

## 1. 拆分前：一个文件装了五样东西

第 3.2 章的 `ch03_02_example.py` 里有：异常类、`parse_guess`、`GuessGame`、`play`、`if __name__ == "__main__":` 入口。它们变化的原因各不相同：

| 内容 | 什么时候需要改 |
|---|---|
| 异常类 | 错误的分类变了 |
| `parse_guess`、`GuessGame` | **游戏规则**变了（范围、次数、提示） |
| `play` | **界面**变了（换措辞、换成网页） |
| 入口 | **启动方式**变了（加命令行参数、读配置） |

**一个模块只应该因为一种原因被修改。** 改措辞的人不应该需要打开规则代码，改规则的人也不应该担心会弄坏界面。

## 2. 拆分后：四个模块，一个方向

```text
m03_structure/guess/
├── __init__.py    只有一段说明，不导入任何东西
├── __main__.py    入口：创建 GuessGame，交给 play
├── cli.py         交互：play(game, ask, say)
├── rules.py       规则：parse_guess、GuessGame
└── errors.py      异常：GuessError 及其子类、GameOverError
```

`ch03_03_example.py` 用第 3.1 章练习 3、4 的参考答案扫描了这个包：

```text
$ python -m m03_structure.ch03_03_example
1. 包内依赖
   __main__   → cli, rules
   cli        → errors, rules
   rules      → errors
   errors     → （不依赖包内任何模块）
2. 反向依赖： 没有
   循环依赖： 没有
3. 直接调用 input/print 的模块： 没有
   把 input/print 当默认值的： {'cli': ['play() 的默认值用了 input', 'play() 的默认值用了 print']}
4. 二分法玩家猜 1-100 的每一个答案：全部猜中=True，最多 7 次，平均 5.80 次
```

```text
__main__  →  cli  →  rules  →  errors
    └──────────────→  rules
```

**箭头全部朝下。** `rules` 不导入 `cli`，它根本不知道有一个命令行界面在用它。

**异常为什么单独一个模块**：`cli` 要 `except GuessError`，`rules` 要 `raise GuessFormatError`。如果异常定义在 `rules` 里，没问题；如果定义在 `cli` 里，`rules` 就得导入 `cli`，箭头朝上了。放在最底层的 `errors.py`，谁都能导入，不会形成环。这就是第 3.1 章循环导入的「解法 1：拆出第三个模块」。

`test_m03.py` 把这些检查写成了测试（`test_ch03_03_dependency_direction`、`test_ch03_03_no_direct_io_anywhere`），以后谁在 `rules.py` 里加了一句 `from m03_structure.guess.cli import ...`，测试会立刻失败。**分层规则写在文档里会被忘掉，写成测试才守得住。**

## 3. 每一层放什么，不放什么

| 层 | 放什么 | 不放什么 |
|---|---|---|
| **入口** `__main__.py` | 读命令行参数、创建对象、把它们连起来 | 规则、交互细节 |
| **交互** `cli.py` | 提示语、输出格式、读输入、把异常翻译成人话 | 「大了还是小了」这种判断 |
| **规则** `rules.py` | 校验、计算、状态 | `input()`、`print()`、文件、网络 |
| **基础** `errors.py` | 异常类型 | 任何逻辑 |

`cli.py` 里确实出现了 `input` 和 `print`，但只是作为 `play` 的**默认参数**（第 1.6 章的依赖注入）。整个包里没有一处直接调用它们，所以 `play` 也能在测试里用假的 `ask`/`say` 跑。

> **数据层在哪？** Day20 的三层是「配置 / 客户端 / 入口」，教科书常说「表现 / 业务 / 数据」。
> 猜数字目前不存任何东西，所以还没有数据层。M4 给游戏加历史记录时，
> `history.py` 会作为规则层下面的一层出现，同样只能被上层导入。

## 4. 检验：换一种界面要改几个文件

`ch03_03_example.py` 里写了第二个「界面」：一个用二分法自己猜的程序。

```python
def bisect_player(game: GuessGame) -> list[int]:
    lo, hi = game.low, game.high
    while not game.is_over:
        mid = (lo + hi) // 2
        result = game.guess(mid)
        if result == "小了":
            lo = mid + 1
        elif result == "大了":
            hi = mid - 1
    return game.history
```

**它只导入了 `rules`，`cli.py` 一行没改。** 实测它对 1-100 的每一个答案都在 7 次以内猜中（`2**7 = 128 > 100`），平均 5.80 次。

这就是分层的收益。规则如果写在 `play` 的循环里，这个程序就得把规则复制一遍，以后改规则要改两处。

## 5. `__main__.py` 与空的 `__init__.py`

```powershell
python -m m03_structure.guess       # 运行包：执行 guess/__main__.py
python -m m03_structure.guess 42    # 带一个参数当随机种子，复现同一局
```

`python -m 包名` 会找这个包里的 `__main__.py` 当主程序运行。所以入口文件起名 `__main__.py`，用户不需要知道里面有哪些模块。

**`__init__.py` 为什么要空着**：第 3.1 章讲过，导入包里任何子模块之前都会先执行 `__init__.py`。在里面导入东西有两种后果，都实测过：

| `__init__.py` 里写了 | `python -m 包名` 时 |
|---|---|
| `from 包 import __main__` | `__main__.py` **执行两次**，并给出 `RuntimeWarning: '包.__main__' found in sys.modules after import of package ...` |
| `from 包 import cli` | 不报警告，但**任何人导入这个包的任何模块，都会连带加载 `cli`** |

第二种是很常见的写法，目的是让外部写 `from m03_structure.guess import play` 更短。代价是只想用规则的人（比如二分法玩家）也得加载交互层。这门课选择保持为空。测试 `test_ch03_03_run_package_with_dash_m` 检查了运行时没有警告。

**一、`game_logic.py` 顶层留着 `print("启动了")`。** Day10 做「导入会执行顶层代码」的实验时加的，一直没删。现在从仓库根目录实测：

```text

```

业务模块被导入一次就打印一次。拆分后的 `rules.py` 没有任何顶层语句，只有定义。

**二、`test_game.py` 一条测试都没跑过。** 断言写在 `if __name__ == "__main__":` 里，pytest 导入时整块跳过，`collected 0 items`。第 2.3 章已经讲过。分层只是让规则「可以」被测试，测试本身还得按 pytest 的规则写。

## 7. 别拆过头

分层的目的是让修改的影响范围变小，不是文件越多越好。三种拆过头的信号：

| 信号 | 问题 |
|---|---|
| 一个函数一个文件 | 读代码要来回跳，没有减少任何修改的范围 |
| `utils.py` / `common.py` 越来越大 | 放不下的都往里塞，它会被所有模块导入，变成新的「什么都管」 |
| 两个模块总是一起改 | 它们其实是同一个职责，应该合并 |

**判断标准还是第 1 节那句：按「修改的原因」拆。** 猜数字拆成四个模块，是因为确实有四种互不相关的修改原因。

## 常见错误

| # | 错误 | 表现 | 怎么避免 |
|---|---|---|---|
| 1 | 规则里直接 `print` / `input` | 测试要模拟键盘；换界面要改规则 | 规则只返回值、抛异常 |
| 2 | **下层导入上层** | 循环导入；或者规则离不开界面 | 共用的东西下沉到更底层的模块；写成测试守住方向 |
| 3 | 异常定义在交互层 | 规则层为了 `raise` 不得不导入交互层 | 异常放最底层的独立模块 |
| 4 | 业务模块有顶层语句 | 一导入就产生副作用（Day10 的 `print("启动了")`） | 顶层只有定义 |
| 5 | `__init__.py` 里导入 `__main__` 或交互层 | 前者：`-m` 运行时执行两次并警告；后者：用规则也连带加载界面 | `__init__.py` 保持为空 |
| 6 | 拆过头 | 文件很多，改一个功能还是要动一串文件 | 按修改原因拆，总是一起改的就合并 |

<summary>参考答案</summary>

1. 看它**因为什么原因需要修改**。规则变了才改的放规则层，界面变了才改的放交互层，启动方式变了才改的放入口。
2. `__main__ → cli → rules → errors`，`__main__` 也直接用 `rules`，只能上层导入下层。`cli` 要捕获异常、`rules` 要抛出异常，异常定义在任何一方都会让另一方导入它；定义在交互层的话，规则层就得反向导入交互层。放在最底层的独立模块，两边都能导入，不会形成环。
3. 规则层是 `rules.py`，`cli.py` 本来就是交互层，交互层负责 I/O。而且它们只是 `play` 的**默认参数**，测试时可以换成假的 `ask`/`say`，所以整个包没有一处直接调用 `input()`/`print()`。
4. 换一种使用方式（不问人、自己猜）只需要导入规则层，交互层一行不改，规则也不用复制。最多 7 次：每次排除一半，`2**7 = 128 > 100`。实测 1-100 全部在 7 次内猜中，平均 5.80 次。
5. 包里的 `__main__.py`。

7. **写成测试。** `test_m03.py` 用静态分析检查依赖方向和 I/O 调用，有人加了反向导入，测试立刻失败。
8. 一个函数一个文件；`utils.py` 越来越大；两个模块总是一起改。
